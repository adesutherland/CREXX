Interpretation boundary:
  The generated and hand-prepared scanners are close on the one-call buffer:
  generated is 1.086x/1.032x slower on rxtvm/rxbvm.  The lexer therefore did
  not remove the dominant prepared-engine cost.  The generated row path is
  10.480x/9.660x slower than hand-prepared because the generated normalize
  method declares 6,455 locals.  Recycled VM frame activation relinks every
  declared local, so 20,034 calls add an O(calls * generated-locals) cost.
  The optimized method is 172,334 RXAS lines (8,446,068 bytes) and contains
  73 JUMPI dispatches, so SELECT did lower to optimized dispatch; dispatch
  absence is not the explanation.

Conclusion:
  This Level B loop/select lowering is a correct generator proof, not a viable
  hot-path representation.  It does not disprove prepared Unicode
  classification mathematically.  A successor must bound live/register state
  independently of DFA size and must reduce the shared output/order engine's
  per-scalar work before another performance claim.
