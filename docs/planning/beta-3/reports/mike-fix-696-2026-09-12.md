# Issue 696: reject exposed globals outside declared storage

Mike's assembler report reproduces on the published
`ed9a5ee70a5bd15f4d56f9a6c6300e0f59510b15` head. An RXAS source that exposes
`g0` without a `.globals` directive exits with signal 11 and emits no
diagnostic. The control source that declares `.globals=1` and exposes `g0`
succeeds.

## Reproduced mechanism

`rxasexre()` detected that the register number was outside
`context->binary.globals` and recorded the existing range error, but continued
processing the invalid declaration. It added the external name and then
indexed `context->extern_regs` with the invalid register number. When global
storage was omitted or declared as zero, that map was null; an upper-bound
register could instead index beyond the allocated map.

The crash therefore occurred after the assembler had already identified the
input error. It was not an accepted RXAS construct, a compiler-output contract,
or a load-dependent test failure.

## Repair

The exposed-global handler now rejects register numbers below zero or greater
than or equal to the declared global count, records the existing diagnostic,
and returns before changing external-name, register-map, or constant-pool
state. Valid exposed globals retain the same path and binary representation.

RXAS source syntax tokenizes a global register as `g` followed by one or more
digits, so a negative register cannot be written in an RXAS file. The handler
still checks the signed 64-bit token value defensively. No syntax, bytecode, or
language-design decision changes.

## Regression and qualification

`rxas_exposed_global_bounds` covers four rejected inputs:

- `g0` with no `.globals` directive;
- `g0` with `.globals=0`;
- `g1` with `.globals=1`;
- `g2147483647` with `.globals=1`.

Every rejected case must exit unsuccessfully, emit the established global
range diagnostic, and leave no output binary. A `.globals=1` / `g0` boundary
control must succeed and produce its binary.
