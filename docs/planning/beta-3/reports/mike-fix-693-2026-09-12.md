# Issue 693: isolated workers lose provider discovery

Mike reported Linux container failures in the published concurrency-provider and
taskwork examples when run through `crexx`, while local tasks and the supplied
Python `ADDRESS CREXX` example passed. The report used master
`48ebc1f610a948a39972348379fd02fff4b156ad`. Repository/account access is a
separate question; this investigation does not attribute the failure to it.

## Reproduction and cause

At `7394206dafeadb4c4d70642a89bff93c9c6a65ed`, a minimal process task returning
`double(21)` succeeds through the plain VM with library/classlib inputs. Running
the same compiled image through the embedded VM used by `crexx` loses its worker
before task execution. A retained snapshot and exact request-envelope replay
under LLDB establish `RXVM_EXECUTOR_PROGRAM_LOAD_FAILED`, with:

```text
ERROR: required RXPA provider rxid for rxid.uuid4 (module Id) was not resolved; searched: <none>
```

The embedded core library includes modules with declarative provider requirements,
even when the user's task only performs integer arithmetic. The controller has a
trusted provider search configuration, but its isolated worker creates a file-backed
executor with no provider path. This independently reproduces the mechanism on
macOS; Linux container restrictions are not needed to explain it.

The repair copies the controller's existing provider path when opening the pool,
passes it as a private worker argument, and applies it to both source and execution
contexts in each fresh executor. The original executor entry point keeps its empty
path default. The current protocol frame format, public syntax and native-handle
boundary are unchanged. All allocation, failed-open and teardown paths release the
copied configuration.

## Regression and qualification

`crexx_process_runtime` exercises Mike's provider and taskwork examples plus a
native `Id.uuid()` task, an expected task conversion failure and subsequent reuse
of the same process pool. Each source runs through explicit compile/assemble with
compiler optimization enabled and disabled, then through plain and both embedded
VM variants; a fresh build also runs through the actual `crexx` driver. Existing
classlib documentation tests retain explicit linking and both VM modes. The new
regression checks exact output and exit status, with bounded process waits.

- The permanent regression passes all 21 executions in Debug and Release.
  Its pre-fix Release negative control fails on the provider-bearing plain-VM
  path after worker transport loss; the retained worker replay identifies the
  missing provider lookup as the cause.
- Full normal Debug correctness QA passed **2,301/2,301** in 615.65 seconds,
  excluding only the separate `performance-measurement` lane. It includes the
  new regression, both process channel fixtures, crash/replacement, and the
  documentation examples in both compiler and VM modes.
- The maintained Apple ASan process panel passed **12/12** in 149.57 seconds,
  including the new 21-execution regression, both process channel fixtures,
  crash/replacement and both documentation examples in both modes. Apple ASan
  does not provide LeakSanitizer; Linux ASan/LSan remains a hosted gate.
- A retained manifest of code, test and build-source hashes remained unchanged
  throughout qualification. Completed normal Debug QA need not be repeated for
  this evidence-only documentation update or the ensuing commit.
- Exact-publication-SHA hosted build, deep-QA, CodeQL and sanitizer results are
  tracked on [#693](https://github.com/adesutherland/CREXX/issues/693). Local
  qualification does not establish release readiness or close #695.

## Separate finding

[#695](https://github.com/adesutherland/CREXX/issues/695) retains a cleanup hang
observed after pre-STARTED transport loss: the terminal request has been observed,
but the controller waits again with an empty unobserved-ticket list. Deliberately
removing the candidate worker's provider path reproduces it. An ordinary failed
task reports state 2, and a conversion failure in DO PARALLEL raises TASK_FAILURE
with exit 27. The exact cleanup mechanism is still under investigation. Fixing
provider discovery does not close that separate error-path issue.
