# Issue 686: complete types for imported globals

The [same-namespace report](https://github.com/adesutherland/CREXX/issues/686)
reproduces on product source at `987d990506e90a5f01ea6a2fb20b46c434c27fe8`.
Both compiler modes accept the nine-line source alone and reject it with an
identical sibling. This is independent of the optimizer failure in #689.

## Cause and correction

Source-global extraction used `type_nm(symbol->type)`, turning the concrete
`.stem` contract into `.object` and omitting array shape. The global resolver
then copied only that base type. A debugger stop in `sym_imva()` shows the
consumer's `shared.s` initially has `TP_UNKNOWN` and no class name, while the
import record supplies `.object`. Resolving that incomplete type prevents the
later factory/index operations from acquiring the correct class contract.

Source extraction now uses the existing `sym_2tp()` serializer, matching binary
global metadata. Resolution parses the retained declaration through the normal
grammar and preserves class, dimensions/bounds and reference information.
Compatibility checks compare complete types. An unknown imported contract does
not erase an already established local type. No namespace, syntax, ABI or
bytecode-format rule changes.

The retained `global_import_types` CTest compiles, assembles, links and runs an
application alone and with a duplicate source sibling. It retains the exact nine-line inference order from the original report
as a separate compile check; adding an entry point that calls `Make` first can
mask that failure by resolving the local class sooner.
Both optimization modes must print `hello:value:42:7`, exercising an object,
a growable scalar array, a bounded two-dimensional array and an object array.
The test also requires exit 2 and a type diagnostic for incompatible global
array bounds. Its inputs are isolated from other source examples. Binary global
contracts are not qualified by this patch: the separate
[#694](https://github.com/adesutherland/CREXX/issues/694) records a pre-existing
source-to-binary global metadata omission and import crash. The binary import
reader also checks for global exports while walking the metadata chain, although
exports use a separate chain. A typed binary fixture alone would therefore give
false coverage; that repair and its regression belong to #694.
